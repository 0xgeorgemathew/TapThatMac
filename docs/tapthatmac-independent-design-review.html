A capable utility with competing signals.

The main design debt is understanding readiness, not inventing a new visual identity.

“Is it listening, did it recognize my tap, and will it run an action?”

These are separate questions. Give each a stable place and a plain answer.

Major

Readiness is distributed across the window.

Pause, Enable system actions, the graph’s live status and the footer describe different layers of state. A prominent preview banner and a consequence-aware footer make the relationship explicit. This is a comprehension finding, not proof of accidental execution.

Major

The visual emphasis favors signal over outcome.

Tuning makes the graph the largest element. Retain it for diagnosis, but promote waiting, recognized, settling and disconnected states into readable text outside the plot.

Major

The ring is recognizable but text is small.

At its defined size, 10 pt labels and translucent material are a legibility risk. Increase type and compare a stable backing against varied desktops before retaining blur.

Polish

Precision and save consequences need consistency.

Use 0.0175 g everywhere for the same threshold. Bring dataset replacement wording next to Save dataset, where the user makes the decision.

Recognition feedback

Waiting for a double-tap

Keep still briefly, then tap twice. Preview mode will not run an action.

“Ignored near typing” requires a confirmed suppression event. Never infer rejection reasons from graph peaks. Keep the last confirmed result visible until a new result or reset, with an event timestamp.

State precedence proposal: show all active blockers in details; choose the actionable headline from recording, user pause, connection/access problems, simulation or low rate, then settings preview. Preserve the existing action guards. Inactive-session, calibration and starting states are included in the examples; test combined blockers against the actual lifecycle before implementation.

One native visual system.

Mint carries identity. Typography, grouping and state labels carry meaning.

Color and materials

The current ring defines mint as RGB 0.38 / 0.83 / 0.72. Keep that identity on dark surfaces; use a deeper related green for readable controls on light surfaces. Status must also have text or an icon.

App surfaces use semantic macOS colors. Graph amber remains a functional threshold color. The opaque ring is an evaluation candidate, not a claim that blur must be removed.

Type, spacing and interaction

  • Type: system font; 24 pt page titles, 13 pt body, 12 pt helper copy. Ring: 12 pt sector labels and 17 pt selected title.
  • Spacing: 20–24 pt page insets; 12–16 pt between related controls; larger separation between tasks. Preserve scroll access at the 720 × 640 minimum.
  • Shape: 10 pt grouped regions in the app; native button shapes. The ring is the only circular command surface.
  • Motion: retain the 450 ms single-tap window, 220 ms ring commit and approximately 620 ms direct-action sequence. Do not tune detection timing as a styling change.
  • Accessibility: preserve keyboard cycling, selected traits, graph adjustment, Reduce Motion and Reduce Transparency. Verify VoiceOver announcements and focus return.

Diagnostics and menu

Follow-through

Reuse the existing recent-activity export on Advanced. Retain the native menu and its labels; align its status wording with settings.Missed tap → Save last 15 seconds is discoverable. Empty events and export failures have explicit text. File saving remains local and no new telemetry is introduced.

Behavior to preserve

  • Actions pause in settings and recordings; simulation uses dry runs.
  • All existing action choices and experimental caveats remain available.
  • Single tap moves after the double-tap window; double-tap selects without advancing first.
  • Arrow navigation wraps; Return chooses; Escape and focus loss cancel.
  • Recordings do not automatically train the detector. Sensor compatibility and lower-rate reliability remain unproven beyond existing evidence.

Validation before app implementation ships

  • Tests for footer/readiness derivation, simultaneous blockers, permission return and disconnected sensor.
  • Regression checks for tap timing, preview safety and cancellation during commit.
  • Threshold synchronization and clamp boundaries; replacement-cancel and failed-save paths.
  • Visual review at 720 × 640 and 760 × 800, in both appearances, with long status text.
  • VoiceOver, keyboard-only operation, increased contrast, reduced motion and transparency on the real app.

The review was iterative.

Design Taste Frontend guided the document’s hierarchy and refinement. Native product decisions stayed grounded in the app’s behavior.

Evidence audit

Extract the existing system first.

Read the source views, menu, action availability and timing. Render five settings pages and the ring using an inert model. Keep original navigation and ring positions. Current dials, inferred: variance 3 / motion 4 / density 6.

Initial proposal

Separate preview, recognition and execution.

Create native component examples with larger ring text, a preview banner, stronger recognition feedback and nearby recovery or save instructions. Choose a restrained direction, not a web-dashboard treatment.

Visual correction

Recover space for the actual controls.

The first proposal pushed Actions and Tuning controls below the fold. Reduce grouping gaps and row padding; shorten the graph from the initial 185 pt proposal to 160 pt. Keep lower-priority details scrollable. Align the permission fixtures for a fair comparison.

Document validation

Inspect the artifact people will read.

Verified the desktop layout and a 375 px browser frame, both document themes, all six comparison tabs, image enlargement and interactive state examples. The browser resize API timed out, so narrow-layout inspection used a same-origin frame. Native prototypes are visual evidence; they do not validate production sensors, permissions or action execution.
