One mode, one dependable gesture

Choose ChatGPT in TapThatX. The app shows the selected conversation, what needs approval, and which actions can run. Double-tap approves the displayed request once. When no eligible request exists, the same gesture does nothing.

The first scope includes Approve once, Decline, and Open request, with pause and connection recovery. Media controls, lock, the command ring, dictation, prompt recipes, and other assistants are omitted from this proposal. Existing app features are not removed by this documentation change.

The sidebar is back. Its earlier omission was a conservative choice, not a rejection of the idea. In this focused design it gives ChatGPT a stable home, alongside connection, tap setup, and activity. There is no second hierarchy of five segmented tabs inside it.

The report’s styling is stripped back: white page, system font, ordinary headings, neutral controls. No appearance toggle, decorative gradients, color-token catalog, or animated presentation. The visual examples carry the design discussion.

Evidence boundary. The current screenshot comes from the earlier source-rendered fixture. Proposed screens and all requests below are illustrative. Research includes official product documentation and read-only inspection of installed ChatGPT application resources. No real approval, keyboard pairing, app configuration, or sensor session was performed.

What custom keyboards actually teach us

The useful pattern is a two-way connection: physical intent travels to the app; current task state travels back to the control surface. A key labeled “Approve” is only one part of that system.

Work Louder × OpenAI: the closest reference

Codex Micro works directly with the ChatGPT desktop app. Its Agent Keys expose chat status, while separate Command Keys include approval and decline. Chat selection and command execution are distinct interactions. The documented double-press on an Agent Key brings the selected chat forward; it is not the approval gesture we propose for TapThatX. Official Codex Micro guide.

Read-only inspection of this Mac’s app bundle corroborates the architecture: a hardware service, HID event subscription, per-thread lighting updates, a command dispatcher, and separate states for awaiting approval versus awaiting a response. This is evidence of a real contextual integration inside the app; it does not establish a public interface for third-party gesture apps.

Honor: show state before action, distinguish a question from an approval, keep the selected task stable, and acknowledge unavailable actions. Leave out: six chat slots, configurable keycaps, voice, joystick mappings, and an expansive command catalog.

Logitech MX Keypad: app-aware controls and agent feedback

Logitech’s 8 September 2026 announcement describes customizable AI controls and community Codex/Claude plugins with real-time agent status. Its product page describes switching controls with the active app. The developer account also acknowledges that state APIs are still incomplete across tools. This supports capability checks, not a promise that every assistant has the same integration. Launch announcement · Product behavior · Developer account.

Honor: controls follow verified app context and show their current availability. TapThatX’s explicit ChatGPT mode should remain selected when focus changes, but approval must disarm.

QMK: hardware events need a host-side companion

QMK’s Raw HID interface supports bidirectional communication with a host program. That enables software to interpret input and send state back. It is transport, not a ChatGPT approval API. TapThatX already supplies the physical input through motion detection, so the missing work is mostly the application adapter and state model. QMK Raw HID documentation.

Stream Deck: do not confuse a profile with deep integration

The Elgato marketplace lists a ChatGPT profile by Kron, with Windows compatibility. That listing alone does not prove request-aware approval or macOS support. It is a useful distinction: a command layout can look integrated while still relying on shortcuts. Marketplace listing.

ChatGPT’s documented shortcuts are conditional

The current command reference lists Return to approve and Escape to decline when an approval request is open. Outside that context the same keys can do something else. TapThatX should never inject Return globally as its definition of approval. Official command reference.

Connected-app permissions and the requested action also affect which confirmation is shown. A one-time approval must not select a persistent allow option or change workspace policy. Managing app permissions.

What “deep integration” means here

Recommended destination: a local, request-aware adapter that publishes available actions and sends a decision for an identified request. The UI above is the contract that adapter must satisfy. It is not evidence that a production bridge already exists.

The app-server approval path includes the request’s thread/turn/item context and supports one-time decisions. A request-resolution event means the request was answered or cleared; it does not alone prove our approval won. Correlate our decision and the subsequent outcome. Official app-server protocol.

Permission hooks are another documented mechanism, but they operate within a supported execution path and can resolve requests before the normal prompt appears. Treat them as a scoped research option, not an external “approve any ChatGPT prompt” endpoint. No automatic allow hook is proposed. Official hooks documentation.

MCP is not a shortcut around this problem. Exposing a TapThatX tool to ChatGPT supplies a tool; it does not by itself subscribe TapThatX to other tools’ approval requests. A model-triggered tool call must not count as the human’s physical gesture.

Connection is a capability check

  1. User selects ChatGPT mode. Detect the installed app and its version; show the selected target.
  2. Check the adapter’s supported build and permission requirements. “App detected” is different from “Approval available”.
  3. Run a harmless test request in a dedicated test conversation. Verify request discovery, scope, decision, and outcome together.
  4. Enable only capabilities that passed. Unsupported versions or unknown prompts show “Open request” with a reason.
  5. On app update, reconnect, wake, or adapter restart, invalidate old requests and check again.

Local finding: /Applications/ChatGPT.app reported version 26.903.71938 and bundle ID com.openai.codex during inspection. The existing identifier is correct for this installation. Do not infer the product from its bundle ID, or assume this identity covers every ChatGPT build.

Internal request record · proposed, not an OpenAI schema

Target:    adapter + app process/session + window + conversation
Request:   provider request ID, or a limited UI fingerprint
Content:   action title + full details + permission scope
State:     inspecting | waiting | sending | resolved | unknown
Decisions: explicit one-time approve / decline capabilities
Gesture:   unique event ID + target/request snapshot
Outcome:   submitted decision + matching acknowledgment or uncertainty

A UI fingerprint must include the prompt container, request details and scope, not just button labels. It can detect some changes but is weaker than a provider request ID. If the adapter cannot identify or validate the target reliably, gesture approval remains unavailable.

Minimum adapter contract and execution sequence
  1. observeTarget returns a complete snapshot, supported actions and reasons for unavailable actions. Event subscriptions are preferred. A fallback refresh is bounded and runs only in ChatGPT mode for the selected target.
  2. validateRequest compares the current target and request against the gesture snapshot immediately before dispatch.
  3. submitDecision receives a request identity, one-time scope and a gesture ID. It allows one in-flight decision per request. Do not queue duplicate gestures.
  4. observeOutcome distinguishes transport acceptance from the assistant accepting the decision, cancellation by another surface, and completion of the underlying task.
  5. Disconnect, focus change, mode change, sleep, lock, Settings opening, or a new request invalidates the snapshot. Never replay an uncertain submission automatically.

No new abstraction framework is needed: keep a focused request model, adapter, coordinator and view. Preserve the current sensor and gesture recognition paths.

Single tap: no navigation and no approval in this mode. Do not move the selection while waiting for the second impact. Start both taps from the same eligible request. If eligibility appears between taps, ask for a fresh double-tap.

Decline: an explicit button for the same verified request. No separate impact pattern in this scope. Closing the companion only dismisses the panel; it does not decline the request. Escape retains the host app’s contextual behavior; TapThatX does not intercept it globally.

Arming: choosing the mode opts into this mapping, but each request must be selected and reviewable. For the initial compatibility adapter, require ChatGPT to be foreground with the approval visible. Merely showing an alert cannot establish that the user reviewed it.

Once: approve only the offered one-time decision. Never normalize “Always allow”, “Allow this session”, permission amendments, or a grouped grant into “Approve once”. If the actual scope cannot be represented accurately, leave it to ChatGPT.

Timing: preserve the current recognizer until physical testing supports changes. The keyboard’s documented timing is not evidence for accelerometer timing. Measure incidental impacts, typing, desk movement and device variation before enabling real approvals by default.

Feedback that stays truthful

The menu bar can say ChatGPT · Waiting for approval. A compact, non-activating panel shows the request title and an Open request action. A background request cannot be approved through that notification alone. Once the user returns to the verified prompt, the panel can show the gesture hint.

After a decision, show “Approved once” only when verified; show the subsequent task status separately. If confirmation is missing, retain “Couldn’t confirm approval” in Activity. Ordinary success feedback can fade; uncertain outcomes remain retrievable.

Activity records the time, request identifier, selected action and delivery result. Keep request text ephemeral by default; redact command arguments, filenames and account details from routine logs. Do not export chat contents or capture the screen just to provide gesture control.

Build sequence and acceptance criteria

  1. Prove the adapter first. Read-only capability spike against the installed version. Establish a supported connection or explicitly limit the Accessibility route. Do not start by building a large settings UI.
  2. Implement request identity. Test replacement, ambiguity, multiple windows, permission scope and acknowledgment with controlled fixtures.
  3. Add ChatGPT mode and sidebar. Keep Settings as a paused environment. Make the separate approval companion the live surface.
  4. Connect the gesture. Bind the double-tap to the request snapshot, deduplicate it, and provide explicit result feedback.
  5. Validate on hardware and real prompts. Use harmless approvals before expanding prompt coverage. Publish a tested compatibility matrix.

Definition of done: in ChatGPT mode, a person can identify the pending action, approve it once with a deliberate double-tap, and understand whether the decision reached the intended request. Anything weaker stays labeled as a compatibility prototype.
